# Book-analysis workflow

## Background

The book-analysis module’s goal is not to turn a book into several long reviews. It helps writing beginners convert a reference work into reusable creative knowledge: work positioning, main-line structure, character system, world setup, thematic expression, technique, and commercial selling points. Because analysis input is usually long text, LLM cost rises clearly with book size, original-text fragment count, and enabled sections. If the UI does not explain scope and cost first, users easily start a large task without knowing the price.

Analysis results also enter the knowledge base, writing-formula assets, or Creative Hub citation paths, so they must serve two needs at once: users can read them directly, and later systems can retrieve and reuse them stably.

## Decision

Book analysis defaults to “original-text range + analysis-dimension presets + visible cost + per-section generation + structured key conclusions”. The user first chooses the document version and an optional chapter range, then which analysis dimensions to generate this time. The system estimates fragment count and model-call scale from the actual input range. Each section generates both readable Markdown and fixed-field `structuredData` for UI summaries, publish, export, and later RAG recall.

Prompt contracts, structured post-processing, and UI / export field labels must share one field spec, so Prompt does not ask the model for one field set, the service normalize another, and the frontend display a third.

## Current Rule

- The book-analysis entry must show how task cost relates to document size, at least word count, estimated original-text fragments, and approximate model-call scale.
- Every new analysis must carry a token-budget cap. The default budget comes from backend `BOOK_ANALYSIS_BUDGET_TOKENS`. Historical rows with `budgetTokens = null` are treated as unlimited. Generation should accumulate `usedTokens` after each section. When the budget is exceeded, mark failure as `budget_exceeded`, keep completed sections, and do not dispatch new section tasks.
- The analysis budget can be adjusted on the detail page. Adjusting the budget only changes `budgetTokens` and must not clear `usedTokens`, because cumulative usage explains historical spend and remaining room. Archived analyses cannot adjust budget.
- Analyses that failed or were cancelled with `budget_exceeded` may “raise the budget and resume”. That path must first write the new budget cap, then re-queue the task. It only reruns non-frozen, unsuccessful sections. `succeeded` and `frozen` sections keep original content and status.
- Regenerating after failure should not overwrite already `succeeded` sections. Rebuild only returns non-frozen, unsuccessful sections to `idle`, so recovery after budget exhaustion, cancel, or partial failure prefers filling gaps.
- Analysis-dimension presets lower beginner decision load:
  - `Quick Analysis`: a low-cost first look at whether the work is worth a deeper analysis.
  - `Standard Analysis`: the default recommended range for most web-novel reference analysis.
  - `Complete Analysis`: deep review or when a timeline section is needed.
- Preset cards should show which sections will be generated, not only a count. Beginners need to know what they will get before accepting the cost.
- `overview` is the minimum required section. Even on a lighter range, keep the overview so the result has work positioning and an overall judgment.
- Knowledge-document versions may be cached by chapter as `DocumentChapter`. Chapter split should prefer deterministic Chinese chapter-title rules; when those rules cannot split reliably, a registered Prompt LLM fallback may run; if LLM still fails, fall back to the whole text as one chapter so old documents and non-fiction documents remain usable.
- `DocumentChapter` is cached at the `KnowledgeDocumentVersion` boundary, recording `chapterIndex`, title, original-text start/end offset, word count, and an optional summary. It does not attach directly to `BookAnalysis`. Multiple analyses of the same source version can reuse the chapter cache.
- `BookAnalysis.sourceRange` is one analysis task’s input boundary, not a reader filter. With no chapter range, analyze the full text. With a chapter range, persist start/end `chapterIndex`, original-text offset, and display labels. Source notes cut only that range. Evidence location still returns to original-text offsets on the full `KnowledgeDocumentVersion.content`, so dual-pane reading and publish provenance are not lost.
- Full analysis generation should use a two-stage path of `overview -> other sections concurrent`. If `overview` is enabled, generate the overview first and extract `BookAnalysisOverviewContext`, then use whole-book positioning, genre, selling points, target readers, strengths, and weaknesses as the later sections’ framing anchor. If `overview` fails, later sections must continue with `null` context. If the user cancels after overview, stop before entering later concurrency.
- When rerunning a non-`overview` section, read the currently saved `overview` prose and structured data, reassemble `BookAnalysisOverviewContext`, and pass it into that section Prompt. If a historical analysis has no usable overview, degrade to `null` context and continue.
- Two-stage switching must keep a run heartbeat and cancel checks. Progress advances monotonically from the notes-stage end, through overview, then remaining sections, so the UI does not see progress go backward.
- Book analysis supports user intervention without changing the evidence boundary: `BookAnalysis.userFocusInstruction` is this analysis’s global focus and should enter every section prompt. `BookAnalysisSection.focusInstruction` is a single-section focus and enters only that section prompt. Both instruction types may only affect selection and expression priority. They must not override evidence grounding, the fixed structuredData schema, or the current section’s duty.
- Disabled sections should stay in the task structure as frozen sections instead of disappearing from the product model, so later local fill does not break the analysis list or publish logic.
- A frozen section with no prose, human edit, or structured conclusion means “not chosen for this run”. It is not a failure or a gap to fill. Completeness denominators count only non-frozen sections planned for this run. Frozen sections that already have content stay as readable results and are clearly marked frozen.
- Each section Prompt input should carry only notes fields related to that section. Fall back to full notes only when no related signal is found, so one section does not repeatedly ingest the whole analysis notebook.
- `BookAnalysisSourceCache` unique keys must include source scope. Full-text cache uses `full`; chapter-range cache uses a stable range key. A partial analysis must not reuse full-text notes, and a full-text rerun must not reuse partial notes.
- `structuredData` is the machine-read layer, not a copy of Markdown prose. Fields should be short, stable, and filterable. When evidence is missing, strings return empty string and arrays return empty array.
- Ordinary `structuredData` array fields keep at most 12 items; timeline-node arrays keep at most 30. Prompts should ask the model to keep the most reusable items by importance and narrative order. If backend normalization still sees an overlong array, keep only items within the cap and write the field name into `normalizationWarnings` so the UI can tell the user.
- Timeline-section `timeNodes` and `eventOrder` should use structured node arrays. Each node at least has `label`, optionally `timeHint`, `phase`, and `sourceRefs`. Old string arrays must be auto-wrapped as `{ label }` in the normalization layer, so historical analyses do not go empty in UI, export, or continuation citations.
- Book-analysis structured field specs, labels, backend normalization, and Prompt fixed-structure examples should come from `shared/types/bookAnalysis.ts`. Do not start another field table in the frontend, export service, or Prompt. English labels are the only stored values.
- Timeline-node compatibility normalization and grouping by phase should go through `shared/utils/bookAnalysisTimeline.ts`. UI summaries, export/publish, and continuation references must not each copy `normalizeTimelineNode`, or historical string nodes, `sourceRefs` truncation, and ungrouped fallbacks will fork.
- Newly generated section evidence should bind to a concrete `structuredData` field when possible. `fieldKey` must come from the current section’s field spec. Array fields may use `fieldIndex` to point at a concrete array item. When normalization sees an illegal field name, only clear the binding; do not delete the evidence itself, so historical data and occasional dirty model values stay readable.
- Evidence `fieldIndex` must sit inside the normalized field-array length. If the model pointed at an index that was truncated, clear `fieldIndex` but keep the evidence item and a legal `fieldKey`.
- Evidence may carry `chapterIndex` and `excerptOffsetRange` pointing at original chapters and excerpt location. After generation, prefer deterministic matching of the evidence excerpt in the source document to fill location. If matching fails, keep the evidence itself; do not drop it because chapter location is missing.
- The UI evidence panel should tolerate two evidence kinds: with chapter location, provide original-chapter preview and excerpt highlight; historical evidence without `chapterIndex` or offset still shows the original excerpt.
- The `character_system` section is part of the analysis report. It helps the user quickly understand the character system, relationship tension, and reusable character design. It should not carry every deep character material.
- Deep character dossiers use independent `BookAnalysisCharacter` / `BookAnalysisCharacterArc` / `BookAnalysisCharacterScene` entities, coexisting with the `character_system` section. Users generate or manually maintain character dossiers when they need to study characterization. Full analysis does not auto-generate deep character dossiers by default, so basic analysis cost is not silently enlarged.
- Deep character dossiers should use a two-stage flow of “candidate recognition -> generate dossier on demand”. `BookAnalysisCharacter.status = candidate` means only the candidate, location, importance, brief, and appearance-chapter hints are saved. `generated` means a full `profileJson`, arcs, and scenes exist. `failed` means the last generation failed and retry is allowed. `generating` is only a brief in-flight state for synchronous generation.
- Candidate recognition and dossier generation both count toward `BookAnalysis.usedTokens`, but they are optional research actions. They must not change `BookAnalysis.status` or trigger rebuild of basic analysis sections. Batch-generating candidates only processes `candidate` / `failed` characters and skips already `generated` dossiers.
- `profileJson` may be empty at the candidate stage. Server serialization must return a non-empty `profile` fallback object to the frontend, at least `name` and `role`, so historical UI or candidate cards are not blank before a full dossier exists.
- This phase carries deep-dossier scene performance as a `sceneLabel` string and does not attach formal scene entities. Arc nodes may cite `chapterIndex`, but leave it empty when there is no chapter-judgment evidence instead of guessing.
- Character-dossier Prompts must go through Prompt Registry. The service layer may only call registered assets and structured-output schemas. Do not inline a business prompt in the character service.
- Character-dossier depth uses four levels: `brief / standard / deep / exhaustive`. `brief` and `standard` mainly use source notes and the `character_system` skeleton. `deep` and `exhaustive` must keep the notes skeleton and, by character dimension, recall original-text chunks through RAG to fill dialogue, action, psychology, and chapter evidence. Raising depth must not degrade into longer notes concatenation, and must not invent beyond original-text evidence.
- Character-dossier dimensions should use `shared/types/bookAnalysisCharacter.ts` as the only enum source. When adding a dimension, first extend the shared type, structured-output schema, and Prompt Registry asset, then let service, route, and UI consume the same definition. Do not bypass AI structured output with temporary string branches in frontend or service.
- Deep-dossier `profileSectionsJson` is a per-dimension block that can be deepened independently. `depthMetadataJson` records the depth, tokens, and chunk citations actually used per dimension. Character evidence in `evidenceJson` should carry `sourceType`, `chapterIndex`, `quote`, optional `chunkId` / `noteSegmentId`, and `dimension`, so the frontend can render evidence and later jump to chapters uniformly.
- Character-related RAG retrieval should close in the character RAG adapter. Deep dossiers use `character.deep` semantics; appearance scans use `character.appearance` semantics. Retrieval queries may be built from character name, dimension, and chapter hints, but recall should keep traceable evidence. Do not treat chunks as unsourced ordinary prompt text.
- Appearance-dimension RAG queries must use appearance-specific phrases, for example looks, countenance, body shape, hair color, eye color, clothing, outfit, accessories, scars, expression, temperament, and posture. Do not mix in dialogue or psychology recall terms, or character speech and inner activity will be mistaken for visual evidence.
- Character appearance evolution is an optional incremental research action on the character dossier. It is not part of basic full analysis. After the user chooses a target coverage rate, the system incrementally fills snapshots by appearance chapters. Already scanned chapters should not be consumed again. `manuallyEdited` snapshots must not be overwritten by later scans.
- Appearance-evolution scans are minute-scale AI tasks. The HTTP entry must only validate and enqueue, then return scan-job status. Actual RAG, chapter-snapshot extract, and merge summary run in the background. The frontend should poll job status and `GET /appearance` for incremental results. Do not treat the user request connection as the long-task lifecycle.
- Appearance coverage is “generated appearance-snapshot chapter count / total character appearance chapters”. The chapter total should come from the intersection of appearance-chapter hints and the chapter cache. If there is not enough appearance-chapter evidence, degrade over available chapters, but do not forge snapshots to pad a percentage.
- Each appearance snapshot describes only that chapter’s looks, clothing, accessories, body state, mental presence, and scene anchors. Cross-chapter stable traits and change strategy write back to `BookAnalysisCharacterAppearance`. Stable traits keep later image-prompt character consistency; chapter snapshots show that chapter’s state.
- Each appearance snapshot may also produce short appearance candidate terms. Terms store only reviewable visual information such as stable traits, chapter state, clothing change, accessories, scars, expression/temperament, or posture. Pure plot action, temporary emotion, and scene atmosphere should not enter the term pool. Candidate terms start as `pending`. Already `rejected` or `merged` terms must not be pushed back to pending by later scans.
- Writing appearance terms back into the character dossier must be an explicit user selection plus a merge trigger. The merge flow must use the structured merge prompt in Prompt Registry. AI judges how current appearance, stable traits, term evidence, and conflicts merge. The server only validates structured output, writes the transaction, and updates status. Do not replace AI merge judgment with fixed string rules.
- After a successful appearance-term merge, update `BookAnalysisCharacter.profileJson.appearance` and `BookAnalysisCharacterAppearance.consolidatedAppearanceJson` together, and mark participating terms `merged`. Selected terms the AI judges unfit for long-term appearance may be marked `rejected`, with the reason written into merge notes for the frontend.
- Appearance-snapshot images still belong to `ImageSceneType = book_analysis_character` and `bookAnalysisCharacterId`, and `BookAnalysisCharacterAppearanceImage` records the relationship among snapshot, generation task, and final `ImageAsset`. While queued, only `generationTaskId` is allowed; after the task succeeds, fill `imageAssetId`, so the UI does not lose snapshot context during generation.
- Chapter appearance-snapshot images should prefer the same analysis character’s base portrait, to keep face shape, hairstyle, posture, and signature details consistent. When multiple base portraits exist, the frontend should let the user choose the reference image for this run. Default may be the primary or first image, but must not force it back after the user clears the selection.
- Reference-image selection must enter both image-generation preview and the final generation task. Preview lets the user confirm which reference materials will be sent. Task execution should resolve same-owner `ImageAsset` records through `ImageGenerationTask.referenceImageAssetIdsJson`, prefer local file paths to the image provider, and write the actually used reference asset ids into the snapshot-image relation and generated-asset metadata for later provenance.
- Book-analysis character images use a separate `book_analysis_character` image scene type. Image tasks and image assets must belong to `BookAnalysisCharacter`. They must not reuse the formal character library’s `character` owner.
- Book-analysis character image generation should live inside the deep character-dossier card and reuse the image module’s confirm-style prompt, task polling, primary image, delete, and sort rules. Basic full analysis does not auto-trigger character image generation.
- Promoting a book-analysis character into the formal character library must be an explicit user trigger. The first version only copies shared person fields and by default may carry the current primary image. Carrying the primary image should clone it as a new `BaseCharacter` image asset. The formal character must not reference the analysis character’s original asset.
- Book-analysis characters and promoted formal characters do not bi-sync. Deleting or editing analysis-character images must not affect already promoted characters. Later formal-character edits also do not write back to the analysis dossier.
- A book-analysis character may be the subject of an “original-text evidence-constrained interview”, but a chapter anchor must be set first, and only materials with chapter evidence at or before that anchor may be read. Dialogue does not change original text, analysis conclusions, or any novel prose. Shared interaction boundaries are in [Universal character subjects and cross-source character conversation](./universal-character-conversation.md).
- Diagnostic mode only changes the entry and display copy. It does not fork the core analysis generation chain. After the user chooses their own novel, the system should export current chapter prose as a `KnowledgeDocument`, then create analysis through the existing `createAnalysis(documentId)` path.
- Diagnostic-mode source documents should prefer the novel-prose TXT export, not a full project export that includes setting, task logs, and quality reports, so pacing, character, and foreshadowing conclusions rest on manuscript prose rather than production-process material.
- Diagnostic mode must not modify original novel prose, and must not auto-write diagnosis results back into planning, characters, or chapters. Later revision still requires the user to explicitly trigger the matching writing/repair path.
- The server book-analysis module uses `BookAnalysisService.ts` and `bookAnalysis.generation.ts` as stable facades. The root directory should not keep stacking same-prefix files. Commands/queries/watchdogs belong in `application/`, budget and source-notes cache in `caching/`, queue/concurrency/progress/serialization in `infrastructure/`, publish and export in `publish/`, config/constants/types/schema/normalization in `shared/`, and section writing in `writing/`. New capabilities should first choose the owning directory, so Prompt calls, cache, state transitions, and HTTP-visible side effects are not piled back onto the facade.
- The frontend analysis workbench’s stable external entry is `useBookAnalysisWorkspace`. That hook should keep page-facade duty and delegate section drafts and optimization preview, deep character dossiers, and publish / writing-formula actions to child hooks. Page components keep depending only on the workspace facade, so character, publish, or section-edit state does not scatter across multiple top-level components.
- When publishing to the knowledge base or exporting Markdown, prefer including a “key conclusions” summary before the long analysis, so later RAG more easily recalls actionable conclusions rather than only long commentary.
- Publishing analysis to the knowledge base must use a separate source channel. User-uploaded material uses `KnowledgeDocument.kind = user_upload`. Published analysis material uses `KnowledgeDocument.kind = analysis_published` and writes a unique `sourceAnalysisId`. Ordinary uploads may keep appending versions by title, but must not merge into analysis-published documents. Analysis publish must reuse the same knowledge document by `sourceAnalysisId` and append a new version.
- When a published analysis enters knowledge-base indexing, structured key conclusions should become RAG facet chunks: genre, selling points, target readers, strengths, weaknesses, character function, and chapter anchors must enter chunk metadata / Qdrant payload. Markdown prose is still used for reading and ordinary retrieval; structured chunks are for later exact recall by dimension.
- Republishing the same analysis into the same novel knowledge base should replace that analysis source’s old binding, so only the latest published version enters the novel RAG binding set. The old published document body is not cascade-deleted, to avoid breaking other citations or historical audit. Binding updates should clean old bindings by `sourceAnalysisId` and published-document ID, so manually binding the same published document does not create a duplicate binding.
- The analysis UI should show structured key conclusions first, then full Markdown. Beginners judge value from conclusions first, then read the long text when they need detail.
- `BookAnalysis.status` is task-orchestration status, not the same as result readability. The frontend must also check each section’s `editedContent / aiContent / structuredData`. A failed, cancelled, or still-running task that already has readable sections should keep a “View existing results” entry. A task that shows success with no readable content should warn that the result is abnormal and offer task details or regenerate.
- Viewing analysis results should prefer a reading-first structure: main sections use tabs and by default show only the current section, instead of stacking every section. Key conclusions are visible by default. Prose density is controlled by a “Highlights / Full reading” switch. Copy, rebuild, publish, export, generate writing formula, and archive belong in the top sticky toolbar. Edit, AI optimize, and notes should stay collapsed until needed. Evidence should embed as field chips inside the section; clicking opens the excerpt and original-text location in the current section, so scanning is not interrupted by a global long panel.
- The analysis result page uses two mutually exclusive top-level views: “Section analysis / Character dossiers”. The top sticky toolbar renders at the Page layer and shares every task action and budget-adjustment entry across views. View state syncs with URL `?view=sections|characters`, so refresh and share links return to the matching view. Illegal URL values fall back to default `sections`. Switching views does not keep the previous view’s local state (selected evidence, dual-pane toggle). DetailPanel and CharacterPanel unmount and remount through conditional render. The dual-pane toggle is enabled only in the `sections` view; the Toolbar hides the dual-pane button in the `characters` view.
- Wide-screen dual-pane comparison belongs only to the analysis-detail reading region. It should not wrap deep character dossiers. The dual-pane toggle may live in the sticky toolbar; when the viewport is insufficient, hide it and auto-degrade to single pane. Preference may persist, but a narrow screen must not force dual pane. The left pane owns original-chapter reading and evidence highlight. The chapter directory should sit beside the prose, not stacked above it. The left pane’s outer layer must clip radius, border, and inner scroll so the border line does not pierce into the right pane. The right pane still hosts section tabs, key conclusions, evidence chips, and prose. The left pane’s current chapter is only a “this chapter” hint for right-side fields. It should not reorder sections or change generation results.
- When source document, chapter cache, or evidence-location reads fail, only degrade original-text comparison. Already saved section prose, structured conclusions, and evidence excerpts must keep showing, and the user should be told that original-text comparison can be retried on its own. Do not project a source error as “there is no analysis result”.
- On medium/narrow screens the current result region must sit before the full history list. The history list is only an auxiliary switcher. After the user picks an analysis from history, the page should switch back to the section view and focus the result region after detail load, so the user does not see several “succeeded” records and cannot find the matching result.
- After a knowledge document is selected, the analysis list should filter by that document. Switching documents must not keep mixing in other documents’ analyses.

## Examples

Recommended:

- When the user chooses a large document, the page explains that longer books usually cost more time and tokens, and gives a model-call estimate for large books.
- When generating the “Character system” section, Prompt input prefers character, plot, and theme signals, and does not force in commercial selling points, world setup, or other low-relevance fields.
- When adding a structured field, first change `BOOK_ANALYSIS_STRUCTURED_FIELD_SPECS` and `BOOK_ANALYSIS_STRUCTURED_FIELD_LABELS`, then let Prompt, normalization, UI, and export consume that definition naturally.
- When publishing analysis results, put short conclusions such as “main-plot summary / conflict escalation / reusable patterns” before section prose, so the knowledge base can retrieve them.

Forbidden:

- Using one checkbox that asks the user to understand an expert decision such as “whether to generate a timeline”, without explaining scope and cost.
- Hard-coding one field JSON in the Prompt, then maintaining another field list in service normalization.
- Stuffing all source notes into every section prompt so one section looks richer.
- Exporting only long Markdown and not structured key conclusions.

## Failure Modes

- Analysis cost is too high: first check enabled section count, document word count, original-text fragment count, notes max-token limit, and whether each section ingested unrelated notes.
- Still running after the budget is exhausted: check whether `BookAnalysisBudgetGuard` runs after section writes, whether `runWithConcurrency` stops dispatching new tasks and waits for already started workers to finish, and whether the UI shows the budget-stop reason from `lastError` `budget_exceeded`.
- After the budget is exhausted the only option is to redo the whole order: check whether the detail page exposes budget adjustment and “raise the budget and resume”; whether the resume API only allows `failed/cancelled + budget_exceeded`; and whether rebuild-section conditions still include `frozen: false` and `status: { not: "succeeded" }`.
- Usage is lost after a budget adjustment: check whether the budget-update path only updates `budgetTokens` and does not reset `usedTokens`. Only ordinary regenerate may reset cumulative usage under from-scratch semantics.
- Later sections disagree with the overview framing: check whether `overview` generated before other sections, whether `BookAnalysisOverviewContext` entered later section prompts, and whether overview failure degraded to `null` context as expected.
- Section content is generic: check whether that section’s notes lack related signals. If they do, go back to the source-note extract prompt or document-segment strategy. Do not let the section writer invent.
- Structured summary is empty: check whether Prompt fixed-structure examples, `BOOK_ANALYSIS_STRUCTURED_FIELD_SPECS`, post-process normalization, and test fixtures agree.
- Structured conclusions were silently truncated: check whether generation wrote `normalizationWarningsJson`, serialization returns `normalizationWarnings`, and the frontend shows matching field names in the key-conclusions region.
- Historical timeline does not display: check whether old string arrays went through the timeline-node wrapper. UI, export, and continuation citations should all tolerate `{ label }` single-field nodes.
- Key conclusions cannot be traced: check whether section evidence has a legal `fieldKey`, and whether array items point at the matching structured entry with 0-based `fieldIndex`. If binding is empty but evidence exists, first check whether model output used a field name not in the current section.
- Deep character-dossier cost is abnormal: check whether character generation was wired into the full-analysis chain. Character dossiers should be triggered only by the user on the character panel, not called automatically inside `runFullAnalysis`.
- Candidate characters duplicate or overwrite generated dossiers: check whether candidate upsert dedupes by normalized name under the same `analysisId`, and whether `generated` characters keep the original dossier instead of being overwritten by recognition results.
- Candidate cards show an empty dossier: check whether `profileJson = null` serialization fallback returns `{ name, role }`, and whether the frontend distinguishes candidate cards from full-dossier cards by `status`.
- Character-dossier content leaves the original text: check whether the character-generation Prompt only uses source notes and `character_system` context, and whether evidence excerpts come from available material. If evidence is missing, lower conclusion certainty or leave empty. Do not invent facts outside the original text.
- A deep dossier looks longer but has no more evidence: check whether `generationDepth` entered the `deep/exhaustive` branch, whether the character RAG adapter returned chunk evidence, whether `profileSectionsJson` recorded dimension depth, and whether `depthMetadataJson` wrote chunkIds and token usage.
- Appearance recall mixed in dialogue or psychology: check whether the character RAG adapter’s appearance query still carries generalized words such as lines, psychology, or action. Appearance dimension should only carry visual terms and chapter hints.
- Appearance scan shows a network failure but snapshots appear later: check whether the scan entry degraded to synchronous HTTP, whether the frontend waited for a full scan response, whether the dev proxy closed the connection early, and whether the scan job is still running in the background. The correct behavior is POST immediately returning a queued/running job, and the UI continuing to poll job and appearance.
- Coverage rises but no new chapters: check whether already scanned snapshots were selected again, whether appearance-chapter total is empty, whether chapter bucketing samples only inside available chapters, and whether `manuallyEdited` snapshots were wrongly treated as overwritable.
- Newly found appearance did not land on the character dossier: check whether the snapshot prompt outputs `candidateTerms`, whether the server saves pending terms, whether the frontend only shows terms awaiting confirmation, and whether the merge API successfully updated character `profile.appearance` and stable traits.
- Terms were wrongly auto-written into character appearance: check whether the scan flow bypassed user confirmation and directly updated `profileJson.appearance`. The correct behavior is scan only generating snapshots and pending terms; write-back happens only after the user selects and merges.
- Appearance-snapshot images do not show on the matching chapter after generation: check whether `BookAnalysisCharacterAppearanceImage.generationTaskId` was written at queue time, whether `ImageGenerationService` filled the waiting snapshot-image record with the new `ImageAsset` when the image task succeeded, and whether serialization include brings out `imageAsset`.
- Chapter appearance images are inconsistent for the same person: check whether the character already has a base portrait, whether the appearance-evolution panel selected a reference image, whether the confirm dialog kept the reference material, whether the generation request wrote `referenceImageAssetIdsJson`, and whether task execution resolved a local reference-image path for the provider.
- Analysis-character images leaked into formal-character images: check whether `ImageSceneType`, task owner, and asset owner use `book_analysis_character` and `bookAnalysisCharacterId`. Only when the user promotes and chooses to carry the primary image should it be copied as a new formal-character image asset.
- Images affect each other after promotion: check whether promotion clones the image file and `ImageAsset` record. Do not only change one asset’s owner, and do not let two characters share the same image record.
- Diagnostic mode accidentally changes the original manuscript: check whether Novel export only creates a knowledge document and an analysis. It should not call chapter update, repair, Auto-Director, or character write-back APIs.
- Diagnosis conclusions mixed in process material: check whether the diagnostic exported Document content comes from chapter-prose TXT, not a full Markdown/JSON project pack.
- Recall is poor after publishing to the knowledge base: check whether exported Markdown includes “key conclusions”, and whether knowledge-base indexing uses the latest published content.
- Republish still recalls the old analysis: check whether `KnowledgeDocument.kind` is `analysis_published`, whether `sourceAnalysisId` wrote the current analysis ID, whether republish created a new version of the same document, and whether that analysis’s old binding under the same novel was unbound. Do not delete the knowledge-document body to fix binding pollution.
- UI decision load is heavy: check whether advanced options sit on the default entry, whether recommended presets are missing, and whether token cost vs book size is unexplained.
- Results are hard to view: check whether main sections still stack vertically instead of using tabs, whether there is no highlights / full-reading switch, whether task actions did not enter the top sticky toolbar, and whether evidence still lives in a global long panel instead of embedding per section. When wide-screen dual pane fails, check viewport detection, localStorage preference, chapter cache, and whether evidence `chapterIndex` / `excerptOffsetRange` are available.
- The task shows success but no result is visible: first check whether the detail API returns sections with prose or structured conclusions. If the data exists, check whether detail-query Loading/Error was wrongly rendered as empty, whether medium/narrow screens put the full history list before results, and whether selecting a record focuses the result region. Do not rerun generation because the page entry is unclear.
- Standard Analysis is shown as a partial failure: check whether completeness counted frozen, empty, unselected sections in the planned denominator. Those sections should show “Not chosen for this run”. Only non-frozen planned sections missing results form a gap to fill.
- Results disappear together when original-text load fails: check whether the result region wrongly depends on the source document or chapter query. Original-text comparison failure may only close dual pane and location ability; it must not block rendering of already saved results.
- The list is messy after switching documents: check whether the frontend list request passes `documentId`, and whether backend `listAnalyses` filters by document.

## Long-term direction

The book-analysis module is evolving from an “all-automatic production tool” into a “user-collaborative research workbench”, covering learning, continuation, and material-library use. The full direction, PR route, and independent character-module expansion are in [Book-analysis module expansion long-term plan](../../plans/book-analysis-expansion-plan.md).

The key expansions already landed are independent deep character dossiers, character images, promotion into the formal character library, and diagnostic mode. Later conversational close reading, incremental catch-up, or multi-book comparison should keep stage boundaries: do not push formal-novel characters, image assets, diagnostic entries, or later research duties back into the basic analysis generation chain.

# Reader-experience contract

## Background

Chapter tasks, boundary contracts, and obligation contracts can guarantee “what this chapter must do”, but they cannot alone guarantee “why a reader wants to finish this chapter and continue to the next”. If prose only consumes task goals, facts, and forbidden zones, the model easily generates chapters that are structurally correct but under-rewarded, with a passive protagonist, no scene turn, or only new hooks.

The reader-experience contract unifies book-level reading promises, volume-level reader payoffs, and chapter-local execution into one structured contract that prose, acceptance, and repair can all consume.

## Decision

Each chapter maintains one `ReaderExperienceContract`. The contract is generated by the chapter-refinement Prompt through structured AI output and stored with `ChapterScenePlan` in the existing `sceneCards` JSON.

Contract fields cover:

- The core question the reader carries into this chapter.
- The visible payoff this chapter must deliver, and its payoff level.
- The protagonist’s immediate desire and main resistance.
- This chapter’s key turn, emotional displacement, and information delivery.
- Net change from chapter start to chapter end.
- Hook responsibilities inherited from the previous chapter or a short arc.
- The continue-reading hook at chapter end.

Scene cards also maintain `resistance / turn / emotionalShift / readerValue`, so a scene is not only information transport or a state transition.

## Current Rule

- A new chapter execution contract must return a complete reader-experience contract and scene-experience fields from AI.
- Writer, acceptance, repair, and patch repair consume the same `reader_experience` context block. They must not each re-interpret a separate reader goal.
- `promisedReward`, `keyTurn`, and `netChange` must be directly perceptible to the reader in the prose.
- `rewardLevel` is the planned visible-payoff intensity for this chapter. Legal values are only `setup`, `partial`, and `major`. It is not the prose’s delivery ratio against the promise, and not a post-hoc completion state. Even if `promisedReward` is fully delivered, do not change it to a nonexistent `full`. Adjust among the three legal levels only when planned payoff intensity mismatches chapter duty.
- `inheritedHookResponsibilities` outrank new hooks. Partial delivery is allowed, but the chapter must not keep adding questions while giving old questions no payoff.
- Ordinary reader-experience gaps belong to chapter-local repair or quality debt. They must not alone trigger global `replan_required`.
- When old chapters lack the new fields, runtime may generate a compatibility projection from existing chapter mission, boundary contract, character goals, open conflicts, and hookTarget. Compatibility projections only serve old assets. New chapters must still rely on AI structured output.

## Context Ownership

- Book Contract: the whole book’s long-term promise to the reader, protagonist fantasy, upgrade ladder, relationship main line, and 3/10/30 chapter stage delivery.
- Volume Strategy: the current volume’s core reader payoff and the whole-book volume-level payoff gradient.
- Reader Experience Contract: how the current chapter turns long-term promises into visible payoff, active action, turn, net change, and hook handoff.
- Chapter Obligation Contract: execution obligations this chapter must hit, keep, touch, and not cross.
- Novel Fact Ledger: irreversible facts that have already occurred and were confirmed by prose observation or acceptance.
- Payoff Ledger: target windows, progress, and delivery state for cross-chapter promises and foreshadowing.
- Timeline: event display, async extract, and diagnostic assets; not writer-prompt required context.

## Compatibility

Phase one does not add database columns. `ChapterScenePlan.readerExperience` and scene-experience fields have old-asset defaults, so old `sceneCards`, old run packs, and recovery records still parse.

The structured generation schema and the compatibility-read schema must stay distinct:

- New AI output missing core fields should be rejected and enter existing semantic retry.
- Old persisted data missing fields should receive defaults. The recovery chain must not crash.

## Failure Modes

- **New chapter still has no contract**: check whether the chapter execution-contract Prompt version, Registry registration version, and structured-output schema agree.
- **Contract exists but the writer cannot see it**: check whether `reader_experience` entered writer required groups, and whether the context Broker allows that group.
- **Rewrite destroys existing payoffs**: check whether repair context consumes the same contract, and require already delivered `readerValue` to be kept.
- **Review suggestion shows `rewardLevel=full`**: this misreads payoff intensity as delivery completion. Check whether the chapter task-sheet quality Prompt keeps the enum and semantic boundary. Do not write that suggestion back into the contract; `full` is not part of the structured contract schema.
- **Volume planning has a payoff, chapter runtime loses it**: check whether `strategyPlan` in the current volume `sourceVersion.contentJson` was restored into `VolumeWindowContext`.
- **Old-chapter recovery fails**: check whether compatibility read wrongly used the strict schema that only applies to new generation results.
- **Ordinary reading-feel issues block the whole book**: check whether acceptance wrongly escalated a reader-experience gap to `needs_manual_review` or `replan_required`.

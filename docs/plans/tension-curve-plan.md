# Rhythm Tension-Curve Plan (P1)

## Priority and prerequisites

**Priority: P1 (important, but do not start immediately).**

The current-stage mainline is still continuing to strengthen each module’s robustness and flexibility (hardening such as chapter-production-chain stability, state-backfill reliability, writing-style engine and context-assembly robustness). This plan does not start implementation until those hardening efforts have reached a staged convergence; it is first captured as a design document so the idea is not lost.

Before starting this plan, the following should hold:

- Chapter-breakdown / chapter detailing / replan chain has had no high-frequency regressions recently.
- Chapter update APIs and volume-planning draft state in the frontend edit-save chain are stable.

## Background

The rhythm / chapter-breakdown and volume-strategy stages currently have no intuitive presentation of “this volume’s rhythm shape”. Per-chapter conflict-intensity data already exists and already participates in the generation chain:

- `shared/types/novel.ts` `VolumeChapterPlan` already has `conflictLevel?: number | null` and `revealLevel?: number | null` as per-chapter fields.
- When generating the chapter breakdown, AI scores each chapter; chapter detailing, task-sheet quality review, and body-writing prompts (`server/src/prompting/prompts/novel/volume/shared.ts`) all send `conflict level` / `reveal level` into context.
- Frontend chapter cards (`client/src/pages/novels/components/StructuredChapterDetailCard.tsx` etc.) display them as per-chapter numbers.

The problem is that these numbers are buried in card after card of chapters; users cannot see at a glance “is this volume’s midsection too flat” or “are all the climaxes piled into the two chapters before the volume end”. For the target user (a writing beginner), they cannot say “chapter 23’s conflict should be 7”, but they can see at a glance that the curve shape is wrong. This is exactly the most common long-form failure mode: sagging middle, crowded climax, no hook at chapter end.

## Goals

On the rhythm / chapter-breakdown workbench (and a read-only thumbnail on the volume-strategy page), add a **tension curve** whose smallest unit is a chapter:

1. **Display**: X axis = chapter ordinal, Y axis = `conflictLevel`; viewport supports switching “whole volume” and “single rhythm beat”; chapter-to-beat mapping reuses `VolumeBeat`’s existing membership.
2. **Default generation**: the curve comes directly from per-chapter `conflictLevel` already generated by chapter breakdown; no new generation step; chapters with no value present as a break or a gray point.
3. **Manual drag**: dragging a chapter’s point edits that chapter’s `conflictLevel`, saved through the existing chapter-plan update API.
4. **Consumption closed loop**: values that have been manually adjusted are marked “user-anchored”; later chapter detailing, replan, and body generation must respect anchored values, and write “this chapter’s target conflict intensity + relative trend vs neighboring chapters (up / down / flat)” into the prompt.

## Core design decisions

### 1. User-anchored vs AI-generated values (non-negotiable)

- Points the user has dragged persist as **anchored values**, distinguishable in data from AI-generated values (e.g. `conflictLevelSource: "ai" | "user"` or an equivalent mechanism), and visually distinguished in the UI.
- On replan (replan window) and re-breakdown, anchored values enter the prompt as **hard constraints**; AI must not rescore over them; only when the user explicitly “un-anchors” or resets the whole volume do they return to AI custody.
- Reason: without this rule, after launch there will inevitably be the frustration of “the curve I tuned was flattened by one replan” — the same class of “manual edit silently overwritten by an automatic chain” as PR #78’s “manual JSON rules overwritten by feature compilation”. This project already has that history; it must be blocked at design time.

### 2. Draw “shape constraints”, not only points

The curve’s incremental value is in neighbor relations, not single-point numbers:

- Shape health-check hints (pure frontend heuristics are enough to start): N consecutive flat chapters hint “rhythm plateau”; volume end should have the whole-volume peak; each beat interior should have small rises and falls.
- Default reference line: provide a reference shape template by genre (progression / mystery etc.); users fine-tune on the reference line, which is significantly better than dragging points from zero. Reference shape templates can start as hard-coded constants; later consider settling them as configurable assets.

### 3. Multi-series architecture, single-series start

- Phase one only does the `conflictLevel` single curve.
- The frontend curve component is designed as “multi-series”: `revealLevel` is a ready second curve (conflict line + reveal line is a classic pairing in screenwriting tools); later there may be emotion-intensity and other series. Component props reserve a series array so phase two does not rewrite.

## Out of scope

- Do not add an independent “tension” data-model entity; reuse `VolumeChapterPlan.conflictLevel`.
- Phase one does not make `revealLevel` or other parameters into editable curves (architecture reserved only).
- Do not change the replan window-decision algorithm itself in this plan; only feed anchored values as constraint input.
- Do not do a cross-volume whole-book curve (phase-one viewport max is a single volume).

## Step-by-step execution plan (file level)

### Part A: Anchoring semantics and data layer

1. `shared/types/novel.ts`
   - `VolumeChapterPlan` interface adds optional field `conflictLevelSource?: "ai" | "user" | null` (final naming as unified at implementation time; same below).
2. `server/src/prisma/schema.prisma` + `prisma migrate`
   - Add a source-mark column only on the `VolumeChapterPlan` table (String? or equivalent enum); default null treated as "ai". **Do not touch the `Chapter` table** — execution state only consumes the value; it does not need anchoring semantics.
3. `server/src/modules/novel/http/novelHttpSchemas.ts`
   - `volumeChapterSchema` adds optional source-mark input; `updateChapterSchema` is unchanged.
4. `server/src/services/novel/volume/volumeWorkspacePersistence.ts`
   - Write chain passes the source mark through; **key rule**: when the request explicitly carries `conflictLevel` and marks it user, persist "user"; AI generation path persists "ai"; if not carried, keep the current DB value (align with PR #78’s hasOwnProperty judgment pattern, to avoid silent overwrite).
5. Mapping layer (row→DTO places such as `legacyVolumeSource.ts` / `volumeDraftContext.ts`)
   - Read chain brings the source mark out; frontend can see it.

Part A verification: `server` and `shared` typecheck; migration can roll forward; new unit tests cover “explicit user values are not overwritten by the AI path / uncarried fields do not change the current value”.

### Part B: Generation and replan chain respect anchors

1. `server/src/services/novel/volume/volumeChapterListGeneration.ts`
   - On re-breakdown: for chapters that already exist with `conflictLevelSource = "user"`, the post-generation write-back stage keeps the user value and mark; the prompt side injects anchored chapters’ values as known constraints (including a list of chapter ordinals and target values).
2. `server/src/prompting/prompts/novel/volume/chapterDetail.prompts.ts` + `shared.ts`
   - In chapter-detailing context, anchored chapters’ conflict level is labeled “user-specified, must not change”; also add a trend description relative to neighboring chapters (up/down/flat), injected whether anchored or not.
3. Replan chain (`server/src/services/planner/PlannerService.ts` consumption side + replan persist)
   - The anchored-value list inside the replan window enters the replan prompt as a hard constraint; on persist, user-marked chapters keep original value and original mark. **Do not change `ReplanWindowDecisionService`’s window-decision algorithm**.
4. `server/src/services/novel/volume/VolumeChapterSyncService.ts`
   - Confirm planning→execution sync still one-way passes the value; the anchor mark does not enter the `Chapter` table.

Part B verification: add a dedicated test file (under `server/tests/`, e.g. `tensionCurveAnchoring.test.js`) — cover three assertion classes: “re-breakdown does not overwrite user anchors / replan persist keeps anchors / prompt text contains anchor constraints and trend description”; regression-run existing guard tests such as `novelDirectorRecovery` / `directorWorkflowStepCatalog` to confirm zero impact.

### Part C: Curve component and workbench integration

1. `client/src/components/tensionCurve/` (new directory)
   - Multi-series curve component: X axis chapter ordinal, Y axis 0–100; drag-point edit, visual distinction of anchored vs AI points, beat-segment background tint, reference-shape dashed line. Props designed as a series array (phase one only passes the conflictLevel series).
2. `client/src/pages/novels/components/StructuredOutlineTab.tsx` (or `StructuredOutlineWorkspace.tsx`, per existing layout)
   - Wire in the curve block; viewport switch (whole volume / single beat; beat membership from the chapter `beatKey`).
3. `client/src/pages/novels/hooks/useNovelVolumePlanning.draft.ts` + `client/src/api/novel/chapters.ts`
   - Drag landing writes draft state and marks user source; save goes through the existing volume-workspace save chain; do not add an independent save API.
4. Volume-strategy page (corresponding component under `client/src/pages/novels/`)
   - Read-only thumbnail curve (reuse the same component’s readonly mode).

Part C verification: client typecheck + build; UI interaction acceptance left to the user per project rules.

### Part D: Shape health-check and reference templates (phase one may defer)

1. `client/src/components/tensionCurve/` (independent file in the same directory)
   - Pure frontend heuristics: N consecutive flat chapters hint “rhythm plateau”, missing volume-end peak hint, zero-rise-and-fall inside a beat hint.
2. Genre reference-shape template constants (progression / mystery etc.) and overlay display entry.

### Execution order and gates

A → B → C → D strict order; **do not start C until B passes dedicated tests** (prevent a half-finished state of “the curve can be dragged but AI ignores it”). Independent commit after each Part; when B completes, update release notes (user-visible behavior changes from B: anchored values start constraining generation).

## Acceptance dimensions

Accept from three dimensions per the plan collaboration rules:

- **Fit**: whether curve data comes entirely from the existing `conflictLevel` chain (0–100 domain unchanged; no new parallel data source); whether anchoring semantics run through the full “edit—breakdown—detailing—replan—body generation” chain; whether the `Chapter` table stays without anchoring semantics.
- **Completeness**: Parts A–C are phase-one must-haves; Part D may be phase-one wrap-up or deferred.
- **Risk**: focus regression on the replan chain (anchor constraints must not change window-decision behavior), volume-workspace save API compatibility (uncarried fields must not change the current value), and whether the dedicated “user anchors overwritten by the automatic chain” tests truly cover both overwrite paths of breakdown and replan.
